# 测量与归因

## 从现有证据定位

先列出已保存的输入、输出、日志、CSV/JSON、计数器、配置和时钟。转换为 [schema](schema.md) 时保留原记录顺序、首条、异常与缺口；原始数据缺失的阶段用未知表示，不根据预期流程补造时间。

| 要回答的问题 | 最小直接观测 | 不能由此推断 |
|---|---|---|
| 一个任务真实耗时 | 同一单调 wall 时钟的任务入口/返回 | 哪个线程或硬件耗费了全部时间 |
| 当前进程/线程用了多少 CPU | 对应 process/thread CPU 时钟的同域差值 | wall−CPU 等于 GIL、IPC、睡眠或调度 |
| PS 准备/处理耗时 | 精确定义的输入就绪到提交、返回到输出就绪等 wall span | 未埋点的内部子阶段 |
| Python 调 C 的调用时间 | Python 调用前后同域 wall span，命名 `c_call` | C 内核、返回转换、GIL 重新获取各自耗时 |
| C 返回/对象构造耗时 | 能对应实际边界的 C 侧返回构造或桥接层直接 span | 外包装总调用时间就是 C 返回开销 |
| IPC 发送/接收等待 | 同域发送调用或接收等待开始/结束；消息 ID 对齐 | 两台机器未校准时间戳之差是传输延迟 |
| PL 内核持续周期 | IP 同一计数域的启动/完成事件、计数器值与频率来源 | MMIO/DMA/排队/中断开销包含在该周期中 |
| 两个任务之间停了多久 | 同域前任务结束、后任务开始 | 间隙原因就是 GIL；需要额外调度/队列证据 |

`dma_wait`、`pl_wait` 等名称描述被观测 API/区间的等待行为，不等于 PL 纯计算。C 内部、Python 线程、子进程和 IP 时钟没有共同域保证时保持独立结果；不能通过减法拼成互斥瀑布图。可画同域 wall 的互斥阶段图，同时以独立面板展示 CPU/PL 指标。

## 设计最少的诊断埋点

1. 定义任务边界、每个 phase 的实际开始/结束事件及计时 API；给每个 record 稳定 ID 和输入哈希。先确认 serial 模型适用，本分析器不建模多个同时执行任务的 DAG 或吞吐重叠。
2. 只对尚不明确且影响决定的边界增加观测。优先使用已存在的计数器和保存记录；避免每点打印、JSON、哈希、文件 I/O、额外 MMIO、轮询或全局 Python profiler。
3. 用 `BoundedCollector` 在运行前建立固定数量 task/span 槽。输入、哈希、阶段字符串和结果存储在测量前准备。普通模式只调用 `begin_task/end_task`；诊断模式才调用 `begin_span/end_span`。导出阶段才构造报告字典。
4. 明确容量与失败行为。容量满时 `CapacityError`，不覆盖、不扩容、不静默丢点。结束当前任务为无效，停止该次诊断并导出已有槽；容量拒绝计数必须保留。任务异常仍需 `end_task(False, error)`，导出未闭合 span 的原始开始点。
5. wall 包围 CPU 两次读时钟；CPU 区间不含 wall 时钟读取。工具本身仍有函数调用、时钟读取与有界检查开销；不要把 profile 与 boundary-only 直接算加速。需要估计埋点扰动时，可有限重复空边界，并原样保留该测量；不默认从任务时间减去均值噪声。

采集模板仅示范当前主机同步纯 Python 工作。接入板级已有代码时，保持其资源所有权、DMA 生命周期与线程模型；把已采得的 PL 同域周期差在导出时附加到 `pl_samples`，同时声明真实频率来源。模板不会自动启动设备、改 Overlay、绑线程、重启服务或启用性能计数器。

IPC 跨进程实例可分别保存各进程的 clock/source/scope，以消息 ID 对齐。只有平台文档与实际计时保证同一个单调域时，才采用同一 clock ID；未验证时保留独立域，不能因为都调用 `perf_counter_ns` 就假定跨主机可减。进程 CPU 时间也不能代表整个进程树。

## 数值和普通 ABBA

先建立同一批保存输入的参考结果。用数值契约确定 dtype、溢出/舍入、容差和无效值含义，分别核对每个 A/B 实现的每条输出，不能只比较聚合指标、丢弃首条或抹掉无效样本。附带 verifier 面向有限一维实数向量；复杂 dtype、复数、位级/溢出语义需要领域验证器，不能强制转换掩盖差异。

普通计时按 A1→B1→B2→A2 运行，相同保存输入、任务次序、配置与观测口径；A/B implementation 是唯一有意变化的身份。诊断埋点关闭后再运行，记录 wall/CPU 边界、所有 sequence 与 validity。输入、配置或 workload 不相同则只分别描述，不能引用报告中的改善百分比。固定输入集哈希和每条输入哈希只证明所声明字节身份；准备数据时要把 dtype/shape/字节序纳入规范序列化规则。

四次运行的每条和每个连续块都留存，冷启动/第一条、异常、最大值必须可追溯。若任务是 100 Hz，5 条的名义吞吐预算是 50 ms；这不自动意味着单次处理 deadline 为 10 ms，也不意味着设备、DMA 或 Notebook 调度已满足真实实时要求。窗口大小来自用户任务的突发长度、队列和端到端约束，不从示例写死。

聚合平均改善只回答“这组保存记录的任务调用平均 wall 是否变化”。同时看含间隙块尾部、无效计数、max/p95/p99、A1/A2 与 B1/B2 漂移；若需要判断热状态、负载或调度变动，须补充对应证据。工具不会给小样本伪造置信度或把某个百分比设成通用验收阈值。

## 两个独立本地示例

`workloads.py` 提供 `vector_energy`（整数向量平方和）和 `moving_sum`（四点滑动和）。参考实现与候选实现对同输入产生同一整数列表；示例验证数值一致、逐记录保存和分析流程。Python 候选实现是否更快依赖主机和输入，技能不承诺方向。

`make_synthetic.py` 生成的 assets 则完全使用人工时间戳：普通 ABBA 的 B 调用为 A 的 75%，有一条明确无效记录和一个任务间长间隙；阶段样例包含嵌套 c_call/IPC/PL 等待/C 返回及独立 PL 周期。它们的命名来自合成定义，不代表真实 C、IPC 或 PL 已被测到。合成的 25% 改善、主机 demo 测试通过，均不是板卡性能或应用验收证据。
