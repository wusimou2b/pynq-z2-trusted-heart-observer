# 证据口径与项目入口

## 运行与时间

先确认计时原点：冷导入、PS预热、硬件配置、正式窗口、排空和分析压缩通常分开。使用原formal开始/结束标记，不能把Notebook总墙钟或最后一行`time_s`直接当作正式采集时长。

| 层次 | 核对事实 | 常见误判 |
|---|---|---|
| 封装 | 外层attempt/final、输入包身份、run epoch | 包名类似就当成同版 |
| 采集 | raw行数、序号、批次、FIFO字节/指针、真实读取区间 | 软件序号连续就证明ADC没丢样 |
| 配对 | 真实IMU来源、时间区间、年龄、唯一使用规则 | 两路第N点天然同步 |
| 算法 | valid、接触状态、质量窗、IBI、内部BPM | 有BPM就已允许发布 |
| 发布 | output_allowed、最终提交、来源年龄、撤销原因 | 内部BPM或允许计数代替最终发布 |
| 展示 | 状态/曲线来源序号、动态帧、用户屏幕观察 | 软件提交300帧即显示300帧 |
| 收尾 | owner/PS PID和exitcode、forced、各资源停止、实际租约 | 停止请求成功就结束了 |

缺失字段保持未知。不能把未记录CPU时间填成0，也不能把缺测/首帧的无效帧差当静止。

## 项目已出现的schema与位置

本项目源码根由用户提供或从当前工作区定位，不在skill中固定盘符、板子地址或某次哈希。发现`v3b25_integration/`后可读：

- `saved925_case.py`：一个历史包的明确嵌套定位和输入哈希核对示例。其925/1106等计数只属于那次录制。
- `review_spatial_camera_results.py`：先确认worker与journal停止，再回读归档和独立文件、核对包身份的实例。源码含历史目录，不能直接当通用CLI执行。
- `board/joint_exit_report.py`：实际进程句柄关闭后的匹配PID/保存退出证据，及PS、硬件清理分开证明。
- `board/run_owner_schedule60.py`：外层首因、原运行返回与内层ZIP的封装关系。
- `docs/reports/`：找当前目标目录对应的回读报告，日期相近不代表同一次运行。

常见内层成员包括`capture/summary.json`、`capture/raw.csv`、`capture/results.csv`、`run_effective25_display.json`、`concurrent_owner_result.json`；持续包可能再加`continuous-results/`前缀。不能依此假定所有包结构相同。

## 解释断点的顺序

1. raw里是否有这一来源记录；没有时定位采集/FIFO而不是显示。
2. 是否成功配对和通过原始监督；无效时按原原因统计，不删掉后重算成功率。
3. processed是否已经覆盖；尾部未覆盖是积压，不能归类为信号无效。
4. 内部BPM是否存在，质量/接触/峰龄是否允许，最终发布时间是否仍新鲜。
5. 发布正常而曲线不连续时，才进一步核对显示快照/绘制。

区分“最早观察到的故障”与“已证明的根因”。例如Python返回超时可以发生在C已成功ACK之后；仅凭总墙钟无法认定PL慢。

## 本skill工具的界限

`inspect_results.py`在内存中遍历ZIP，检查所读成员CRC，输出JSON叶子事实、CSV行数/字段及明确布尔字段计数；不执行文件，不将任何字段自动升级为验收结论。软件序号统计不是FIFO连续性证明。默认读取限额用于工具资源管理，不是项目的采集门槛；提高限额不改变任何算法或保护政策。
